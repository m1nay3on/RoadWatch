# RoadWatch Challenges and Solutions

This document summarizes key implementation challenges encountered while
building RoadWatch and the solutions currently implemented.

| Challenge | Solution implemented |
|---|---|
| **Enforcing a consistent report lifecycle across citizens, inspectors, and administrators.** Reports move through several statuses, and each role should only perform the actions allowed at that point. Incorrect transitions could allow a case to bypass inspection, assignment, or completion. | Implemented role-aware workflow validation in the backend. Inspector decisions require notes and a supported priority; repair work requires an active assignment; and administrator actions control endorsement and closure. The API rejects unsupported transitions rather than relying only on frontend controls. |
| **Keeping citizens and inspectors informed when more information is required.** A status change alone did not provide a reliable way for the citizen to answer or for the inspector to receive that answer later. | Added a persisted report conversation. Inspector notes are stored as inspector messages, citizens can reply from their report details, and replies are saved with sender and timestamp information. A citizen response moves the report back to **Under Review**, allowing the inspector to review the thread and make another decision. |
| **Allowing citizens to delete only eligible reports.** Citizens need control over reports that have not progressed, while verified, endorsed, and closed reports must remain part of the case record. | Added a delete action with a confirmation dialog for reports in **New** or **Needs Information** status. The backend independently verifies the citizen owns the report and that its status is eligible, and rejects deletion otherwise. Related photos, status logs, verification records, and assignments are removed with the report. |
| **Making report lists manageable as the number of reports grows.** Showing every report category in one long page made it harder for citizens and inspectors to find a case. | Reorganized the citizen’s **My Reports** and the inspector’s **Inspector Reports** pages into status tabs with report counts. Only the selected category’s table is displayed, and tab navigation supports left/right arrow keys. |
| **Showing endorsed cases in the right progress category.** Endorsed reports have a distinct status and were not included by filters that only checked for **Ongoing**. | Updated the citizen and inspector ongoing report lists and dashboard counts to include both **Ongoing** and **Endorsed to Engineering Office** reports. Each report retains its actual status label in the table. |
| **Validating uploaded report evidence.** File names and browser-provided content types alone are not enough to ensure evidence is an allowed image or within size limits. | Added server-side validation for PNG/JPEG image data, filename and type matching, image signatures, maximum file size, and a maximum of five photos per report. |
| **Maintaining useful history for report decisions and completion.** Without an audit trail, it would be difficult to understand who made a decision or when the report changed status. | Stored status changes, inspector verification decisions, assignment details, and completion information in their respective MongoDB collections and report fields. Status history is available through the API and displayed in report timelines. |
| **Preventing unauthorized access to protected actions and data.** Different user roles have different responsibilities, and report owners should not be able to change administrative or inspector-controlled fields. | Added signed expiring bearer tokens and backend role checks on protected routes. Public report creation validates accepted fields and assigns the Citizen role server-side; inspector and administrator routes require the appropriate role. |
| **Keeping registration data valid and accounts safe.** Incorrect contact details, incomplete addresses, underage registrations, and weakly protected passwords could undermine account reliability and security. | Added backend validation for email, age, mobile number, required address fields, and password length. Passwords are stored using scrypt hashes, and new public registrations are always assigned the Citizen role by the server. |
| **Handling different report field formats consistently.** Existing database records use a mixture of naming styles, and MongoDB's internal `_id` should not be confused with the public report ID used by the application. | Added API normalization that maps legacy snake_case fields to camelCase and returns the public report ID without exposing MongoDB `_id`. This helps older records continue to work with the frontend. |
| **Making large report lists easier to browse without breaking older clients.** Users need search, filters, sorting, and pagination, but existing frontend behavior expects an array when no list options are specified. | Added configurable list-query handling for supported search, filter, sort, and pagination options, with validation for unsupported sort fields and invalid page values. Requests without options retain the legacy array response. |
| **Ensuring report submissions contain meaningful information.** Empty or malformed category, location, description, evidence, or assignment values can create unusable records or inconsistent workflow data. | Added server-side validation and normalization for report text and evidence, verifies that selected categories are active, and validates report IDs and inspector email addresses when assignments are created. |
| **Coordinating repair assignments with status changes.** A report should not be marked as actively undergoing repairs until an administrator assigns it, and inspectors should not update another inspector's assigned repair. | Added assignment checks before an **Ongoing** transition. The API verifies an active assignment exists and, for inspectors, confirms the assignment belongs to the authenticated inspector. |
| **Completing and documenting endorsed reports.** Endorsement and closure need to retain who performed each action and when, while keeping the Engineering Office as an external recipient rather than introducing an unsupported application role. | Added administrator-controlled endorsement and closure details, including endorsement recipient, date, actor, optional reference, and closure information. Closing a report also completes any active assignment and records the transition. |
| **Helping users understand report progress.** A status label alone does not explain when a report was submitted, reviewed, verified, endorsed, or completed. | Added status timeline and detail views that surface available review notes, inspector identity, endorsement information, citizen replies, and relevant timestamps. |
| **Reducing clutter while keeping report categories accessible.** Citizen and inspector report tables previously occupied one long page, making navigation cumbersome as the number of cases increased. | Added status tabs with count badges for the citizen and inspector report pages, matching the administrator completion tab style. Keyboard arrow navigation is supported so users can switch tabs without relying only on a mouse. |
| **Verifying that changes do not break existing behavior.** Workflow and data-format changes can affect other screens and API consumers. | Added backend tests for authentication token checks, validation, workflow transitions, report formatting, and list filtering/sorting/pagination. The backend test suite currently passes 13 tests, and the frontend lint and production build have been run after recent UI changes. |

## Remaining Follow-up

The current inspector reports tabs include **Verified**, **Ongoing**, and
**Closed**. A dedicated **Rejected** reports tab is not currently present, so
rejected reports are not separately listed on that page. Add and test that tab
if inspectors need a dedicated view for rejected cases.
